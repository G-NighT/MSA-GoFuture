# ADR-004: Глобальное развёртывание (multi-region), 99.99% доступности и низкая задержка

## Контекст

GoFuture должен обеспечить 99.99% доступности и низкую латентность для пользователей Юго-Восточной Азии (далее SEA) и Южной Америки (далее SA), при развёртывании более чем в 3 географических регионах. Дополнительно требуется усилить периметр защиты (WAF/Firewall и т.п.), определить репликацию данных, геомаршрутизацию и план failover.

Архитектура: микросервисы по доменам + событийная платформа Kafka/Flink (см. Task1 и Task2).

## Требования

1. 99.99% доступности (в т.ч. при падении одного региона).
2. Низкая задержка для SEA и SA (пользователь должен попадать в “ближайший” регион).
3. Multi-region: минимум 4 региона (чтобы было >3 и был отдельный DR/буфер).
4. Определить схему репликации: OLTP данные + события.
5. Geo-routing с health checks и автоматическим failover.
6. Отразить инструменты защиты (WAF, Firewall и аналоги) на C2 (изменения выделить красным).
7. Дополнительно: стратегия комплаенса (data residency, платежи, аудит, шифрование, ретеншн).

## Решение

### 1) Выбор регионов (пример целевого набора)

Цель: закрыть SEA + SA + иметь независимый “опорный” регион для DR/глобальных сервисов.

Рекомендуются следующие 4 региона:

- **SEA-1: Singapore** - хаб SEA, стабильная сетевая инфраструктура, минимальная латентность для части ЮВА.
- **SEA-2: Jakarta** - для снижения латентности в Индонезии/соседних странах и разгрузки SEA-1.
- **SA-1: São Paulo** - крупнейший хаб SA, покрытие Бразилии/соседних стран.
- **US/EU-DR: us-east (Virginia) или eu-west (Ireland)** - “нейтральный” DR/резерв + глобальные интеграции/аналитика (и как запас по ёмкости).

Обоснование:

- Два региона в SEA = устойчивость к региональным деградациям и пиковым нагрузкам + латентность.
- Один регион в SA = минимизация задержки и соблюдение локальных требований (при необходимости data residency).
- Доп. регион (US/EU) = независимость от локальных инцидентов провайдера/кабельных проблем, DR и “control plane”.

> Примечание: конкретные облачные названия можно адаптировать под выбранного провайдера. Важно именно географическое покрытие и независимость доменов отказа.

### 2) Модель развертывания: Active-Active для stateless, “region-primary” для OLTP данных

- **Stateless компоненты (API Gateway/BFF, доменные сервисы, consumers, Flink jobs)**
  - **Active-Active** во всех регионах. Масштабируются горизонтально.
- **OLTP данные**: по умолчанию **“home region”** (данные поездки и платежа закреплены за регионом, где создан заказ).
  - Внутри региона: HA (multi-AZ), синхронная репликация/кластер.
  - Между регионами: асинхронная репликация в DR (для восстановления), и событийная репликация в Kafka (для глобальных read-моделей и аналитики).

Почему так:

- Сильная консистентность между континентами резко увеличит latency (особенно для booking/payment).
- Закрепление сущности за регионом сохраняет низкую задержку и упрощает SLO.
- DR достигается репликацией + event log.

### 3) Схема репликации данных

**OLTP (PostgreSQL per service):**

- В каждом регионе: Primary + Sync Replica (в другой AZ) для быстрых failover внутри региона.
- Между регионами: Async replica в “парный” регион и/или DR регион.
- Для критичных доменов:
  - Booking DB: реплика в DR + периодическая проверка консистентности (reconciliation).
  - Payments DB: реплика + обязательный audit log, сверка с PSP/банками.

**События (Kafka):**

- Kafka кластер в каждом регионе.
- Репликация выбранных топиков:
  - в “глобальный аналитический контур” (ClickHouse/warehouse),
  - при необходимости - в соседний регион для DR (MirrorMaker2 / репликатор).
- Доменные события = “источник правды” для вторичных read-моделей и аналитики.

### 4) Геомаршрутизация

Рекомендуется следующая комбинация:

- **GeoDNS / Latency-based DNS** (или Global Load Balancer/Anycast) - первичная маршрутизация в ближайший регион.
- **Health checks** региональных ingress’ов (L7) - автоматическое исключение деградировавшего региона.
- **Sticky на регион** для сессий и активной поездки:
  - после создания поездки клиент получает `trip_home_region`,
  - дальнейшие запросы по поездке маршрутизируются в тот же регион (через токен/заголовок/маркер в gateway).

### 5) План аварийного переключения (Failover)

**Failover уровня региона (region down):**

- GeoDNS/Global LB исключает регион по health check.
- Новые запросы идут в ближайший живой регион.
- Для активных поездок:
  - если “home region” недоступен, включается режим “degraded”:
    - чтение статуса из DR/реплики (если успела догнаться),
    - либо восстановление из event log (последнее подтверждённое состояние).
  - после восстановления - reconcile/компенсации.

**Failover БД внутри региона:**

- Автоматический failover primary→sync replica (multi-AZ), RPO≈0 внутри региона.
- Сервисы переподключаются через виртуальный endpoint (cluster endpoint).

**Failover Kafka:**

- В регионе: RF=3 (в пределах AZ), auto leader election.
- При полной деградации региона: потребители/продюсеры переключаются на региональный кластер в другом регионе (только для нефункциональных контуров (аналитика/телеметрия) или для DR-восстановления).

### 6) Инструменты защиты (WAF/Firewall) и обоснование

Добавить на периметр:

- **CDN + DDoS protection** (Anycast/edge) - поглощение L3/L4 атак и ускорение статики.
- **WAF** - защита L7 (OWASP Top-10, bot mgmt, rate limiting на уровне правил).
- **Network Firewall** (VPC firewall / security groups / NACL) - сегментация, deny-by-default, контроль east-west.
- **mTLS service-to-service + OIDC** - защита внутренних вызовов и централизованная авторизация.
- **API Gateway policies** - rate limits, JWT validation, schema validation (где возможно).

Почему это важно:

- При мульти-регионе растёт площадь атаки.
- 99.99% требует устойчивости не только к сбоям, но и к атакам/аномалиям трафика.
- L7 WAF снижает риск деградации core-сервисов от ботов/сканеров/инъекций.

## Стратегия комплаенса (доп. часть)

1. **Data residency**: персональные/платёжные данные хранятся в “регионе происхождения” (home region), межрегиональная репликация - только в разрешённые юрисдикции, либо в обезличенном виде.
2. **PCI DSS / платёжная безопасность**:
   - токенизация платёжных данных, минимизация хранения PAN,
   - сегментация сети (cardholder data environment),
   - аудит действий и неизменяемые логи (WORM/immutability).
3. **Шифрование**:
   - in transit (TLS/mTLS),
   - at rest (KMS/HSM), ключи по регионам (BYOK где нужно).
4. **Ретеншн и удаление**:
   - политики хранения логов/трейсов,
   - “право на удаление” (если применимо), data lifecycle.
5. **Доступ и аудит**:
   - RBAC/ABAC, least privilege,
   - централизованный IAM + MFA для админов,
   - журналирование админских операций (особенно Payments/Payouts).
6. **Локальные требования**:
   - локальные фискальные требования/чеки,
   - локальные форматы отчётности,
   - отдельные контуры для интеграций с банками.

## Альтернативы

- Один глобальный регион + CDN: проще, но не даёт низкой латентности и не выполняет требования multi-region и устойчивости.
- Полностью синхронная кросс-региональная БД: проще в логике, но резко увеличивает latency и стоимость.
- Active-Passive: дешевле, но хуже распределение нагрузки и выше RTO при переключении.

## Компромиссы и риски

- Multi-region повышает операционную сложность (наблюдаемость, runbooks, тестирование DR).
- Асинхронная межрегиональная репликация даёт RPO>0: нужно проектировать идемпотентность и компенсации.
- Комплаенс может ограничить репликацию (придётся разделять “PII/Payment” и “telemetry/events”).
