# ADR-001: План доменной декомпозиции монолита GoFuture (год)

## Контекст

GoFuture — агрегатор такси (пассажирское/водительское приложения + корпоративный портал). Сейчас система — монолит на Django с общей PostgreSQL БД и Celery/RabbitMQ.
Монолит ограничивает масштабирование (100k+ активных поездок → каскадные отказы), замедляет delivery (фичи ~полгода), высокий MTTR (>4 часов).
Нужно перейти к микросервисам по доменным границам, соответствующим продуктовым командам:
Booking, Driver, Pricing, Payments, Notification, Geography, Analytics, Fraud.

Цели бизнеса/ИТ (целевое состояние):

- 500k конкурентных поездок
- горизонтальное масштабирование в нескольких регионах
- 99.95% доступности критичных сервисов
- time-to-market фич до 2 недель
- соответствие локальным регуляторным требованиям
- real-time dynamic pricing и “умное” перераспределение водителей
- интеграции с локальными платежами/картами/пушами

## Требования

### Нефункциональные требования (NFR)

**Производительность и масштабирование**

1. Поддержка 500k конкурентных поездок; работа при пиковых всплесках без каскадных отказов.
2. Горизонтальный скейлинг stateless-компонентов, независимый скейлинг доменных сервисов.
3. Мульти-регион: минимум 3 гео-региона, возможность независимого масштабирования по регионам.

**Надёжность и доступность**

4. 99.95% доступности критичных контуров (заказ поездки, назначение водителя, расчёт цены, оплата).
5. Изоляция отказов (circuit breaker, timeouts, bulkheads), graceful degradation.
6. RTO/RPO: для критичных сервисов RTO ≤ 30 минут, RPO ≤ 5 минут (уточняется SRE).

**Данные и согласованность**

7. “Database per service” (логическое/физическое разделение): каждый домен владеет своей моделью.
8. Согласованность — преимущественно eventual consistency; распределённые транзакции через SAGA/оркестрацию.
9. Идемпотентность и дедупликация сообщений/команд (особенно Payments).

**Безопасность и соответствие регуляторике**

10. Централизованный IAM (OIDC/OAuth2), сервис-to-сервис mTLS, секреты в secret-manager.
11. Шифрование in transit и at rest, аудит для чувствительных операций (платежи, выплаты).
12. Локализация данных (data residency) по регионам при необходимости (политики хранения/удаления).

**Наблюдаемость и эксплуатация**

13. End-to-end трассировка (trace-id), корреляция логов/метрик/трейсов.
14. SLO/SLI на доменные сервисы; алерты на пользовательские метрики (заказы/назначения/оплаты).
15. Автоматизация развертывания (blue/green или canary), быстрый rollback.

**Совместимость и миграции**

16. Минимизация downtime: миграции по модели Strangler Fig.
17. Backward compatibility на API (версионирование, совместимые контракты) и на события (schema evolution).
18. Пошаговая миграция данных с backfill + CDC/dual-write (см. файл `ADR-002-Data-Migration-Plan.md`).

## Решение

### Этап 1 (Месяцы 1–2): Проработка NFR и “платформенный фундамент”

- Вводим edge-слой: API Gateway (маршрутизация, rate limits, auth, версии API).
- Единый стандарт наблюдаемости: correlation-id, OpenTelemetry, дашборды и алерты по SLO.
- Подготовка CI/CD шаблонов микросервисов (скелет сервиса, стандарт логирования/метрик, healthchecks).
- Контур безопасности: IAM/OIDC, mTLS между сервисами, политика секретов.
- Базовый контрактный подход: OpenAPI для sync, AsyncAPI + schema registry для событий.

Результат: можно безопасно и предсказуемо “вырезать” сервисы без деградации эксплуатации.

### Этап 2 (Месяцы 2–3): Карта сервисов и доменные границы

Выделяем доменные сервисы по командам (bounded contexts):

1. **Booking Service**

   - Заказ поездки, жизненный цикл поездки (Created/Assigned/InProgress/Completed/Cancelled)
   - Оркестрация с Driver/Pricing/Payments
   - SLA: критичный

2. **Driver Service**

   - Профили/статусы водителей, доступность, гео-статус (последняя позиция через Geography/stream)
   - Управление сессиями/сменами, приём заказа
   - SLA: критичный

3. **Pricing Service**

   - Расчёт тарифа, surge pricing, real-time корректировки
   - Отдельный compute-контур, масштабируется независимо
   - SLA: критичный (для booking flow)

4. **Payments Service** (включая выплаты как поддомен)

   - Платежи пассажиров, возвраты, чеки/инвойсы, интеграция с Яндекс Пэй
   - **Payouts**: выплаты водителям и интеграции с банковскими API
   - SLA: критичный, повышенные требования к идемпотентности/аудиту

5. **Notification Service**

   - Push/SMS/email, шаблоны, предпочтения, ретраи
   - Часто “edge” и слабо связан с core-данными → хороший кандидат на ранний вынос

6. **Geography Service**

   - Геокодинг, маршруты, ETA, интеграция с Яндекс Картами
   - Кэширование результатов, ограничение внешних вызовов

7. **Fraud Service**

   - Скоринг фрода, правила/ML, асинхронные проверки, флаги/блокировки
   - Большая часть — event-driven

8. **Analytics (Realtime) Service**
   - Сбор событий, доставка в ClickHouse, витрины/дашборды, near-real-time
   - Отделён от OLTP, работает по событиям

### Этап 3 (Месяцы 3–12): Очерёдность выделения сервисов (приоритеты) + логика

**Принцип:** сначала “краевые” (edge) и вычислительные сервисы с минимальной связностью и малым риском, затем — чувствительные (payments), и в конце — core-оркестрация (booking).

Порядок (рекомендуемый):

1. **Notification**  
   Обоснование: минимальная связность, stateless/идемпотентные операции, быстрый выигрыш по стабильности и скорости релизов.

2. **Geography**  
   Обоснование: чёткая интеграционная граница (внешние карты/маршрутизация), возможность кэширования, снижение нагрузки на монолит, улучшение SLA (timeouts/circuit breakers на внешние API).

3. **Pricing**  
   Обоснование: compute-контур; можно вынести без полного разрыва данных (вход: параметры спрос/предложение, выход: цена). Даёт эффект на пиках.

4. **Fraud**  
   Обоснование: естественно event-driven, допускает eventual consistency (soft-block/hold), снижает риски финансовых потерь.

5. **Analytics (Realtime ingestion)**  
   Обоснование: отделяет аналитический поток от OLTP, уменьшает нагрузку на основную БД, формирует “event backbone”.

6. **Payments (и Payouts как поддомен)**  
   Обоснование: высокий риск и регуляторика → перенос после появления стабильной платформы (audit, idempotency, retries, DLQ).

7. **Driver**  
   Обоснование: высокая нагрузка и сложные статусы/онлайн-состояние; выгодно вынести после того, как Pricing/Geography готовы поддержать smart-allocation.

8. **Booking (последним)**  
   Обоснование: это “сердце” продукта и интеграционный оркестратор. Выносить последним, когда окружающие сервисы стабильны, чтобы минимизировать downtime и риск каскадных сбоев.

### Этап 5: Механизмы обратной совместимости (backward compatibility)

**API (sync)**

- Вводим **API Gateway** как единый вход для клиентов.
- Стратегия Strangler Fig: gateway маршрутизирует часть эндпоинтов в новые сервисы, остальное идёт в монолит.
- Версионирование API: `/api/v1/...` (совместимые изменения), `/api/v2/...` (breaking).
- Для несовместимых доменных моделей — **Anti-Corruption Layer (ACL)**: адаптеры на границе (в сервисе или в gateway/BFF).

**События (async)**

- Вводим “event backbone” (Kafka/аналог) для доменных событий.
- На монолите: **outbox pattern** → публикация событий из транзакции БД (без потери событий).
- Schema evolution: совместимые изменения, схема в registry, consumer-driven contracts.

**Параллельный режим**

- “Shadow reads”/“dark launch” для некоторых функций: новый сервис обслуживает запрос параллельно, но ответ клиенту идёт от старого до стабилизации.

## Альтернативы

1. “Big bang rewrite” монолита → отвергнуто: слишком высокий риск простоя/регресса.
2. Только “модульный монолит” без сервисов → отвергнуто: недостаточно для мульти-регион и независимого масштабирования.
3. Сначала выносить Booking → отвергнуто: максимальная связность, риск каскадных проблем.

## Компромиссы / риски

- Eventual consistency усложняет бизнес-процессы (SAGA, компенсации, повторная доставка).
- Рост операционной сложности (наблюдаемость, SRE практики, CI/CD, управление контрактами).
- Нужно дисциплинированно избегать “распределённого монолита” (общие БД/общие схемы).
- Переход потребует стандартизации контрактов и строгого управления изменениями.
