# ADR-002: План миграции данных по доменным сервисам (минимальный downtime)

## Контекст

Сейчас все домены живут в общей PostgreSQL БД монолита. Требование — “database per service” и миграция больших объёмов данных без простоев.
Риски: согласованность, распределённые транзакции, регрессии, нагрузка на БД при backfill.

## Требования

- Минимизировать downtime (предпочтительно 0 downtime; допустимы короткие окна для финального cutover, если нужно).
- Сохранить backward compatibility на API и данных во время миграции.
- Поддержать большой объём исторических данных (поездки/платежи/события).
- Обеспечить аудит и идемпотентность (особенно Payments/Payouts).

## Решение: общий подход миграции

Используем комбинацию:

1. **Backfill (batch)**: выгрузка исторических данных из legacy DB → новые БД сервисов.
2. **CDC** (Change Data Capture) или **dual-write** на период синхронизации:
   - CDC предпочтительнее для read-heavy доменов и больших таблиц (минимизирует изменения в монолите).
   - Dual-write применяем точечно там, где проще контролировать корректность в бизнес-логике.
3. **Strangler cutover**:
   - сначала переключаем **чтение** на новый сервис (read switch),
   - затем переключаем **запись** (write switch),
   - после стабилизации — удаляем legacy-код/таблицы.

Технические паттерны:

- **Outbox pattern** для публикации доменных событий из транзакции БД.
- Идемпотентные обработчики (dedup key / event id).
- Версионирование схем событий (schema registry) и миграции схем БД.

## План миграции по сервисам (в порядке внедрения)

> Примечание: точные названия legacy-таблиц зависят от текущей схемы — здесь указан “класс данных”, который нужно привязать к реальным таблицам при инвентаризации.

### 1) Notification Service

- Данные: шаблоны, предпочтения, статусы отправок, токены устройств (если хранятся).
- Источник: legacy DB (пользовательские настройки/таблицы уведомлений) + внешние токены.
- Целевое хранилище: Notification DB (PostgreSQL) + Redis для очередей/ограничений.
- Миграция:
  1. Backfill шаблонов/настроек.
  2. Dual-write из монолита при изменении настроек (короткий период).
  3. Cutover: gateway маршрутизирует notify-эндпоинты в новый сервис.

### 2) Geography Service

- Данные: кэш маршрутов/ETA, настройки провайдера, лимиты.
- Источник: почти нет критичных OLTP-данных (в основном вычисления + кэш).
- Целевое: Redis cache + конфиг в Postgres.
- Миграция: без тяжёлого backfill. Cutover на уровне gateway.

### 3) Pricing Service

- Данные: правила/параметры surge, кэши, агрегаты спрос/предложение.
- Источник: часть параметров в legacy DB + поток событий (поездки/водители).
- Целевое: Postgres + Redis; расчёт по входным сигналам.
- Миграция:
  1. Перенос конфигураций (backfill).
  2. Подключение к event bus для сигналов.
  3. Shadow mode: новый pricing считает параллельно; сравнение результатов.
  4. Cutover на чтение цены клиентом/Booking.

### 4) Fraud Service

- Данные: правила/модели, результаты скоринга, флаги блокировок.
- Источник: legacy DB + события.
- Целевое: Fraud DB.
- Миграция:
  1. Backfill правил/истории (если нужно).
  2. Подписка на события поездок/платежей.
  3. Постепенное включение enforcement (soft-block → hard-block).

### 5) Analytics (Realtime ingestion)

- Данные: события доменов, витрины.
- Источник: event bus + остаточно legacy-таблицы для исторического наполнения.
- Целевое: ClickHouse.
- Миграция:
  1. Историческая заливка (batch) поездок/платежей в ClickHouse.
  2. Realtime ingestion из event bus.
  3. Проверка полноты (reconciliation jobs).

### 6) Payments Service (включая Payouts поддомен)

- Данные: транзакции, статусы платежей, возвраты, инвойсы/чеки, выплаты, аудиторский лог.
- Источник: legacy DB + внешние PSP/банки.
- Целевое: Payments DB (PostgreSQL), отдельные таблицы для аудита и идемпотентности.
- Миграция:
  1. Инвентаризация статусов/идемпотентных ключей и reconciliation-процедур.
  2. Backfill исторических транзакций (batch, по диапазонам дат).
  3. CDC из legacy DB (или dual-write из монолита для новых платежей) + обязательная reconciliation сверка с PSP.
  4. Cutover: сначала новые платежи идут через Payments Service, затем перенос возвратов/выплат.
  5. Окно “финальной синхронизации” допускается для закрытия хвоста (минуты, не часы).

### 7) Driver Service

- Данные: профили, документы/верификации, статусы, активные сессии, агрегаты.
- Источник: legacy DB + события.
- Целевое: Driver DB, online-статусы можно держать в Redis (ephemeral) + журналирование в Postgres.
- Миграция:
  1. Backfill профилей/верификаций.
  2. Параллельное ведение статусов (dual-write или CDC).
  3. Cutover: driver-эндпоинты и принятие заказов → новый сервис.

### 8) Booking Service (последним)

- Данные: поездки/заказы, состояния, назначения, маршруты, расчёты, связи с оплатами.
- Источник: legacy DB (основной объём).
- Целевое: Booking DB.
- Миграция:
  1. Backfill поездок по временным диапазонам (например, “за 12 месяцев” сначала, затем глубже).
  2. CDC для новых/изменённых поездок до cutover.
  3. Постепенное переключение чтения: история поездок → новый сервис, затем активные поездки.
  4. Переключение записи: создание заказа → новый Booking; монолит остаётся только для legacy-остатков.
  5. После стабилизации — деактивация legacy-таблиц/кода.

## Компромиссы / риски

- CDC увеличивает инфраструктурную сложность, но снижает риск ошибок dual-write.
- Dual-write проще начать, но риск рассинхронизации выше (нужны reconciliation и идемпотентность).
- Полный backfill может грузить legacy DB — нужен throttling, окна и реплики для чтения.
- В Booking/Payments потребуется больше времени на тестирование (E2E + “shadow mode”) из-за критичности.
